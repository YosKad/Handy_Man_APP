# 03 — Database Schema

Postgres 16 + `pgvector`. All ids are `uuid` (v7-style time-ordered where
generated by the app). All timestamps are `timestamptz`, UTC. All tables carry
`created_at`, `updated_at`. Soft deletion via `deleted_at` only where the
product needs recovery; privacy deletions are **hard** deletions.

---

## 1. Entity relationship overview

```
users ──1:N── sites ──1:N── projects
  │                             │
  │                             ├─1:N── media_assets
  │                             ├─1:N── analyses ──1:N── analysis_findings
  │                             ├─1:N── guides ──1:N── guide_steps ──1:N── step_progress
  │                             ├─1:N── conversations ──1:N── messages
  │                             └─1:N── jobs
  ├─1:N── consents
  ├─1:N── entitlements
  ├─1:N── credit_ledger
  └─1:N── audit_log

knowledge_documents ──1:N── knowledge_chunks (vector)
materials · fasteners · product_classes · safety_rules   (curated reference data)
ai_calls                                                  (cost/audit ledger)
```

## 2. Core tables

### 2.1 `users`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | uuid PK | |
| `email` | citext UNIQUE | nullable when auth is provider-only |
| `email_verified_at` | timestamptz | |
| `password_hash` | text | argon2id; null for social-only accounts |
| `auth_provider` | text | `password` \| `apple` \| `google` |
| `provider_subject` | text | UNIQUE with `auth_provider` |
| `display_name` | text | |
| `locale` | text | BCP-47, default `en-US` |
| `unit_system` | text | `metric` \| `imperial` |
| `role` | text | `user` \| `pro` \| `admin` |
| `status` | text | `active` \| `suspended` \| `pending_deletion` |
| `deletion_requested_at` | timestamptz | starts the 30-day grace window |
| `last_seen_at` | timestamptz | |

Indexes: `email`, `(auth_provider, provider_subject)`, partial index on
`status = 'pending_deletion'` for the purge job.

### 2.2 `sites` (a home, an apartment, a workshop)

`id`, `user_id` FK, `label`, `kind` (`home`/`rental`/`office`/`other`),
`notes`, `country_code` (drives code/standards defaults — matters for
electrical and fastener conventions).

Every project belongs to a site; a default site is created on first project so
the user is never asked about it up front.

### 2.3 `projects`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | uuid PK | |
| `user_id`, `site_id` | uuid FK | |
| `workflow` | text | `install` \| `repair` \| `advise` |
| `title` | text | AI-suggested, user-editable |
| `status` | text | `draft` → `analyzing` → `needs_input` → `ready` → `in_progress` → `completed` \| `abandoned` \| `failed` |
| `intent_text` | text | the user's own words |
| `active_guide_id` | uuid FK | the revision the user is executing (pinned) |
| `safety_class` | text | `green` \| `yellow` \| `red` (denormalised for list views) |
| `completed_at` | timestamptz | |

Indexes: `(user_id, updated_at desc)` for Home/History, `(status)` for workers.

### 2.4 `media_assets`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | uuid PK | |
| `project_id` | uuid FK nullable | null for advice-only or profile media |
| `user_id` | uuid FK | ownership check without a join |
| `kind` | text | `photo` \| `video_frame` \| `audio` \| `annotated` \| `generated` |
| `role` | text | `product` \| `location` \| `mount` \| `hardware` \| `wide` \| `step_evidence` \| `other` |
| `storage_key` | text | opaque key in object storage; never a public URL |
| `content_type`, `bytes`, `width`, `height` | | |
| `phash` | bigint | perceptual hash → analysis cache key + duplicate detection |
| `exif_stripped` | boolean | must be true before any provider call |
| `consent_id` | uuid FK | which consent record covered this upload |
| `derived_from_id` | uuid FK self | annotated images point at their source |
| `retention_expires_at` | timestamptz | set by policy; purge job honours it |

EXIF (including GPS) is stripped on ingest, before storage and before any
provider call. The original is never persisted with location data.

### 2.5 `analyses` and `analysis_findings`

`analyses`: `id`, `project_id`, `revision` (int), `status`, `schema_version`,
`overall_confidence` (numeric 0–1), `model_provider`, `model_name`,
`prompt_version`, `raw_output` (jsonb, for debugging and regression tests),
`created_at`.

`analysis_findings` — one row per extracted fact, which is what makes the
confidence gate and the "confirm what I saw" UI possible:

| Column | Type | Notes |
| --- | --- | --- |
| `id` | uuid PK | |
| `analysis_id` | uuid FK | |
| `field` | text | e.g. `product.model`, `wall.material`, `mount.vesa`, `product.weight_kg` |
| `value` | jsonb | typed by `field` |
| `unit` | text | nullable |
| `confidence` | numeric(4,3) | |
| `is_safety_critical` | boolean | drives the gate |
| `source` | text | `vision` \| `user` \| `knowledge` \| `rule` |
| `evidence_media_id` | uuid FK | which photo supports it |
| `bbox` | jsonb | normalised `[x,y,w,h]` — also reused for annotation |
| `user_corrected` | boolean | set when the user edits the value |

Unique on `(analysis_id, field)`. A user correction writes a new row with
`source='user'` superseding the vision row, so the correction history is intact.

### 2.6 `guides`, `guide_steps`, `step_progress`

`guides`: `id`, `project_id`, `analysis_id`, `revision`, `schema_version`,
`title`, `summary`, `difficulty` (`easy`/`moderate`/`advanced`),
`estimated_minutes`, `safety_class`, `safety_rationale`, `tools` (jsonb),
`materials` (jsonb — attribute-specified product classes), `prerequisites`
(jsonb), `common_mistakes` (jsonb), `final_verification` (jsonb),
`model_provider`, `model_name`, `prompt_version`, `is_immutable` (true once a
user starts executing it).

`guide_steps`: `id`, `guide_id`, `ordinal`, `title`, `body`, `duration_minutes`,
`safety_note`, `tools` (jsonb), `verification` (text — how the user checks the
step succeeded), `media_id` (annotated image), `spatial_anchors` (jsonb,
reserved for AR), `is_optional`.

`step_progress`: `id`, `project_id`, `guide_step_id`, `user_id`, `state`
(`pending`/`done`/`skipped`/`blocked`), `evidence_media_id`,
`validation_result` (jsonb — the assistant's verdict on the evidence photo),
`completed_at`. Unique on `(project_id, guide_step_id)`.

Regeneration never mutates a guide the user has started: a new `revision` row is
inserted and `projects.active_guide_id` only moves if the user opts in.

### 2.7 `conversations` and `messages`

`conversations`: `id`, `project_id` (nullable for global assistant chats),
`user_id`, `title`, `context_snapshot` (jsonb — the analysis/guide facts the
conversation was grounded in).

`messages`: `id`, `conversation_id`, `role` (`user`/`assistant`/`system`),
`content` (text), `media_ids` (uuid[]), `tool_calls` (jsonb),
`references` (jsonb — knowledge chunks cited), `model_provider`, `model_name`,
`token_usage` (jsonb), `created_at`.

Index: `(conversation_id, created_at)`.

### 2.8 `jobs`

`id`, `user_id`, `project_id`, `kind` (`analyze`/`generate_guide`/`annotate`/
`validate_step`/`advise`/`export`), `status`
(`queued`/`running`/`succeeded`/`failed`/`cancelled`), `progress` (0–100),
`idempotency_key` (unique per user), `payload` (jsonb), `result` (jsonb),
`error_code`, `error_detail`, `attempts`, `started_at`, `finished_at`,
`cost_usd` (numeric(10,6)).

Index: `(status, created_at)` for the worker, `(user_id, created_at desc)` for
the client.

## 3. Knowledge and reference data

### 3.1 `knowledge_documents` / `knowledge_chunks`

`knowledge_documents`: `id`, `source_type` (`manual`/`standard`/`curated`/
`manufacturer_api`), `title`, `publisher`, `product_class_id`, `url`,
`language`, `checksum`, `ingested_at`, `license_note`.

`knowledge_chunks`: `id`, `document_id`, `ordinal`, `content` (text),
`token_count`, `metadata` (jsonb), `embedding vector(1536)`.

```sql
CREATE INDEX knowledge_chunks_embedding_idx
  ON knowledge_chunks USING hnsw (embedding vector_cosine_ops);
```

Retrieval is filtered *then* searched (product class, language, country) so the
vector search operates on a relevant subset. The embedding dimension is stored
per document set so a model change is a new column/table, not a silent
mismatch.

### 3.2 Curated reference tables

These are the deterministic backbone of the safety layer. Curated by humans,
versioned, and citable.

- **`materials`** — wall/substrate types: `drywall`, `plaster_lath`, `concrete`,
  `brick`, `hollow_block`, `tile_over_x`, `wood_stud`, `metal_stud`. Fields:
  `id`, `key`, `display_name`, `visual_cues` (jsonb — helps the vision prompt),
  `drilling_notes`, `hazards` (jsonb).
- **`fasteners`** — anchors/screws with `material_key`, `load_class`,
  `min_thickness_mm`, `pullout_kg_typical`, `requires_pilot_hole`,
  `pilot_diameter_mm`, `notes`, `citation`.
- **`product_classes`** — `tv_wall_mount`, `curtain_rod`, `shelf_bracket`,
  `door_lock`, `faucet`… with `required_attributes` (jsonb) that recommendations
  and material lists are expressed against.
- **`safety_rules`** — `id`, `code`, `scope` (jsonb matcher over analysis
  fields), `classification` (`green`/`yellow`/`red`), `rationale`,
  `citation`, `version`, `active`. Evaluated deterministically; the highest
  severity match wins.

### 3.3 `ai_calls` (cost and audit ledger)

`id`, `user_id`, `project_id`, `job_id`, `purpose`, `provider`, `model`,
`prompt_version`, `input_tokens`, `output_tokens`, `image_count`,
`latency_ms`, `cost_usd`, `status`, `error_code`, `created_at`.

Every provider call writes exactly one row. This table answers "why did this
guide say that", "what does a guide cost", and "did the new prompt regress".

## 4. Accounts, consent, and compliance tables

- **`consents`** — `id`, `user_id`, `kind` (`terms`, `privacy`,
  `image_processing`, `analytics`, `marketing`), `version`, `granted`,
  `granted_at`, `revoked_at`, `ip_hash`, `user_agent`. Uploads reference the
  consent row that authorised them.
- **`audit_log`** — `id`, `actor_user_id`, `actor_type`
  (`user`/`system`/`admin`), `action`, `entity_type`, `entity_id`, `metadata`
  (jsonb), `ip_hash`, `created_at`. Append-only; no updates, no deletes.
- **`data_exports`** — `id`, `user_id`, `status`, `storage_key`,
  `expires_at`, `requested_at`, `completed_at`.
- **`entitlements`** — `id`, `user_id`, `plan` (`free`/`plus`/`pro`),
  `source` (`ios_iap`/`play_iap`/`promo`/`manual`), `status`,
  `current_period_end`, `external_transaction_id`.
- **`credit_ledger`** — `id`, `user_id`, `delta`, `reason`, `job_id`,
  `balance_after`. Append-only; balance is derived, never stored on the user.
- **`feature_flags`** — `key`, `enabled`, `rollout_percent`,
  `targeting` (jsonb).

## 5. Access control

Application-level authorisation is primary: every repository query is scoped by
`user_id` taken from the verified JWT, never from the request body.

Postgres RLS is enabled as defence-in-depth on all user-owned tables:

```sql
ALTER TABLE projects ENABLE ROW LEVEL SECURITY;
CREATE POLICY projects_owner ON projects
  USING (user_id = current_setting('app.current_user_id', true)::uuid);
```

The API sets `app.current_user_id` per transaction. Background workers use a
role that bypasses RLS but is restricted to the tables it needs.

## 6. Retention and deletion

| Data | Retention | Mechanism |
| --- | --- | --- |
| Project media | 24 months after last project activity, or immediately on user delete | `retention_expires_at` + nightly purge job |
| Analyses / guides | Lifetime of the project | cascade with project |
| Conversations | 24 months | purge job |
| `ai_calls` | 13 months, then aggregated and the user id nulled | monthly rollup job |
| `audit_log` | 24 months | rolling partition drop |
| Account deletion | 30-day grace, then hard delete of all user rows + storage objects | `users.status='pending_deletion'` → purge job → tombstone row only |

Deletion is verified: the purge job asserts zero remaining rows across a
generated list of every table carrying `user_id`, and zero remaining storage
objects under the user's prefix, then writes a completion record with no
personal data.

## 7. Migration policy

Alembic, forward-only. Rules:

1. Additive first: add nullable column → backfill → set not-null in a later
   migration. Never a blocking rewrite on a large table.
2. Index creation is `CONCURRENTLY` in production migrations.
3. Every migration is tested against a seeded database in CI (upgrade **and**
   downgrade to the previous revision).
4. Reference data (`materials`, `fasteners`, `safety_rules`) ships as versioned
   seed migrations so a deployment is reproducible.
