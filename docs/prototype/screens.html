HandyAI · Interface prototype · 7 screens

The screens are mostly about what the app refuses to guess.

A person photographs the TV, the mount and the wall. Everything after that is an argument about certainty: what the system read, how sure it is, what it still needs, and when it should stop being helpful and tell them to call someone. That argument is the interface — which is why the confidence meters and the safety notice are the load-bearing components here, not the chrome around them.

Every colour, size, radius and duration below is read from docs/05-design-system.md, so this prototype and the Flutter theme cannot drift apart.

What this is: a working HTML prototype of the specified interface, built to be judged before the Flutter code is written. The step photo in stage 05 is genuine output from the backend's annotation renderer — not a mock-up. Everything else is presentation: no live data, and the Flutter app does not exist yet.

03Confirm what I saw

The screen that turns the worst failure into a five-second fix

Silent misidentification is the failure mode that makes everything downstream confidently wrong. So identification is shown as an editable fact with a confidence bar, never hidden state. The user corrected the model number here; that correction is certain by definition and no later re-analysis can overwrite it.

The weight came back at 62%, under its 80% threshold — and weight decides which anchor is safe. So the app asks for the label, and says why. After two rounds of asking for photos it stops and asks a direct question instead: an endless “one more photo” loop is a worse failure than a question.

What the system is doing The confidence gate in analysis_service.py — thresholds are per-field and higher for anything load-bearing. Nothing generates a guide while a safety-critical field is short.

04Project · amber

Amber means: doable, but a mistake here costs you

The classification is computed by rules, not written by the model. This job is amber because 15.4 kg on plasterboard sits at roughly 75% of what the best cavity anchor will hold — with a 1.25 safety factor applied in code, where no prompt can talk it down.

The pre-flight checklist has to be acknowledged before step 1 opens. Tap any step to expand it, and the checkbox to complete it — the rail fills green behind you and the guide freezes, so nothing shifts under someone halfway through a job.

What the system is doing SafetyClassifier returned load_near_material_limit and picked the fixing: a metal cavity toggle at ~18 kg. The model is allowed to phrase that, not to change it.

05Step · annotated

Their wall, marked up — not a stock diagram of someone else's

This image is real output from the backend. The vision model returns coordinates and labels; the server draws the arrows, drill marks and measurement itself with Pillow. That's about a hundred times cheaper than generative image editing, it's byte-for-byte reproducible, and it physically cannot invent hardware that isn't in the photograph.

Each mark also emits a sentence of alt text, so the overlay reads aloud for a screen reader instead of being a picture with nothing in it.

What the system is doing DeterministicAnnotator composites five marks; the measurement and the cable-zone warning both trace back to cited reference data, not to model prose.

06Assistant

“I can't tell from this photo” is a feature

The assistant is grounded: the project's analysis, the active guide and the current step are pinned into every request, and the client never sends a system prompt. Ask about the screw in your hand and it answers about this job.

It is also prompted and tested to refuse a verdict it can't support. Confident wrong reassurance — “yes, that looks fine” about a fixing that's about to pull out of a wall — is the most damaging thing this product could say, so the interface treats an honest “I can't see enough” as a first-class answer with a way forward.

What the system is doing Streaming over SSE with the step context assembled server-side. Verdict came back unsure, so no judgement is rendered — just a specific ask.

07Referral · red

The screen where the product stops selling itself

Seven categories are hard red lines: mains electrical, gas, water mains, structural, work above about two metres, anything heavy overhead, and asbestos-era surfaces. This bathroom fan is on the electrical one.

The notice can't be dismissed and the step-by-step flow is withheld — not the information. The user still gets what the job involves, what to ask the electrician, and a cost expectation so they aren't walking in blind. Withholding the walkthrough while still being useful is the whole design of this screen.

What the system is doing electrical_mains fired, so the guide is generated but served read-only. The referral copy is human-written and version controlled — a model never drafts a red-line warning.

Tokens in use

Semantic names only — no component references a raw hex

Which is what lets the theme switch above work at all, and what will keep the Flutter theme honest: a custom lint fails the build on a hardcoded colour, size or duration in feature code.

Type scale 34 / 28 / 22 / 17 / 15 / 13 / 12 · radius 8 / 12 / 16 / 24 · spacing on a 4-point grid · motion 120 / 240 / 420 ms, all of which collapse to instant when the reader has Reduce Motion on. Step instructions are set at 17/26 because they're read at arm's length while holding a tool. Everything scales to 200% text size without clipping, and no state anywhere is communicated by colour alone.
